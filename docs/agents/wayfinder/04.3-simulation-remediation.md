# 04.3 Simulation Remediation - Engine Failure Thresholds

## Context / Problem Statement

Currently, the engine simulation runs for a fixed duration regardless of the severity of the faults injected. When a catastrophic physical fault is injected (e.g., severe cooling degradation leading to extreme CHT, or massive misfire causing RPM drop), the simulation continues logging data until the predetermined `max_time`. As a result, the downstream ML pipeline calculates the Remaining Useful Life (RUL) as a simple countdown timer (`max_time - current_time`), training the LSTM model to falsely believe that catastrophically damaged engines survive just as long as perfectly healthy ones.

## Solution

The simulation engine must be updated to inherently recognize catastrophic failure states. When critical telemetry thresholds are breached (e.g., RPM drops below idle, or temperatures exceed structural limits), the simulation should terminate early. This physical termination naturally shortens the generated data file. Consequently, the existing RUL calculation in the ML pipeline will automatically assign correct, responsive labels (reaching 0 at the moment of catastrophic failure).

## User Stories

1. As a Simulation Engineer, I want the engine simulation to halt execution immediately when RPM drops below 1000, so that engine stall conditions are realistically modeled.
2. As a Simulation Engineer, I want the engine simulation to halt execution immediately when Cylinder Head Temperature (CHT) exceeds 250°C, so that catastrophic thermal failure is modeled.
3. As a Simulation Engineer, I want the engine simulation to halt execution immediately when Oil Pressure drops below 20 psi, so that fatal lubrication failure is modeled.
4. As a Simulation Engineer, I want the engine simulation to halt execution immediately when Exhaust Gas Temperature (EGT) exceeds 900°C, so that critical exhaust valve/turbine failure is modeled.
5. As a Simulation Engineer, I want the engine simulation to halt execution immediately when the Vibration Index exceeds 0.9, so that catastrophic structural failure is modeled.
6. As a Data Engineer, I want the telemetry pipeline (`run_pipeline`) to gracefully handle a simulation that terminates early, so that it can export a shorter Parquet file without crashing.
7. As an ML Engineer, I want the generated Parquet files for catastrophically failed missions to be physically shorter than healthy missions, so that the `dataset.py` RUL calculation organically drops to zero at the point of failure.

## Implementation Decisions

- **Modules to be modified**: 
  - `simulation/engine.py` (Core Simulation class)
  - `datasets/generate_mission.py` (Data export pipeline)
- **Architectural approach**:
  - Introduce an explicit state-check mechanism within or immediately following the `Simulation.step()` method.
  - The `Simulation` class will raise a specific `EngineFailureException` (or return an `is_alive=False` flag) when the state dictionary breaches any of the critical thresholds.
  - `run_pipeline` will catch this exception (or check the flag) during its `num_steps` loop and safely break out of the loop early, writing out the telemetry collected up to that exact timestamp.
- **Critical Thresholds**:
  - `rpm` < 1000.0
  - `cht` > 250.0
  - `oil_pressure` < 20.0
  - `egt` > 900.0 (and applicable to individual cylinder `egt_1` to `egt_4`)
  - `vibration_index` > 0.9

## Testing Decisions

- **What makes a good test**: Tests should verify the external behavior of the `Simulation` and the `generate_mission` pipeline without relying on the internal state updates (e.g. we only care that the pipeline halts and output is shorter, not exactly how `tau` filters reached that point).
- **Modules to be tested**:
  - `tests/unit/test_core_physics.py` (or a new `test_engine_failure.py`)
  - `tests/unit/test_mission_profiles.py` (or similar dataset pipeline test)
- **Testing Seams**:
  1. **Simulation Level**: Instantiate a `Simulation`, manually set a state value beyond a critical threshold (or inject a severity 1.0 fault and step forward), and assert that stepping further raises the failure exception or indicates a dead engine.
  2. **Pipeline Level**: Run `generate_single_mission` with a catastrophic fault, and assert that the resulting DataFrame length is strictly less than the length expected from `max_time / dt`.

## Out of Scope

- Modifying the XGBoost or LSTM training scripts (this is handled in Phase 03.3).
- Adding new types of faults or secondary cascade logic (handled in Phase 05.4).
- Creating the dynamic transient mission profiles (handled in Phase 05.4).

## Further Notes

- By keeping the thresholds centralized in `Simulation`, any downstream consumer (like a real-time dashboard or what-if sandbox) will automatically benefit from realistic engine death mechanics.
