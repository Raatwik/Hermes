# [wayfinder:task] Integration: EHI & Dashboard Critical Status Fix

## Problem Statement

When the frontend Operator Dashboard runs live telemetry, the Engine Health Index (EHI) remains perpetually stuck at 0/100, ignoring all telemetry updates. Furthermore, the dashboard's "System Status" constantly triggers false "CRITICAL" alarms. This occurs because the UI calculates deviation against hardcoded static baseline values (e.g., expecting 2450 RPM at all times), whereas the engine's physical behavior fluctuates naturally through varying flight phases (idle, climb, cruise, loiter). This creates a highly confusing and unusable experience where healthy flight maneuvers are incorrectly flagged as critical failures.

## Solution

The integration between the backend physics/ML layer and the frontend state management will be updated to transmit and consume dynamic physics baselines. The backend ML subscriber will calculate what the healthy engine *should* be doing at the current throttle and altitude, and append these baseline values to the MQTT telemetry stream. The frontend will consume these dynamic expected values to calculate deviation accurately. Additionally, the frontend will dynamically calculate the Engine Health Index (EHI) on a 0-100 scale using the `twin_drift_score`.

## User Stories

1. As an Operator, I want the Engine Health Index (EHI) to visibly update as live telemetry comes in, so that I can see the real-time health of the UAV engine at a glance.
2. As an Operator, I want the EHI to decrease proportionally when the digital twin detects drift, so that I can anticipate mechanical wear before a critical fault occurs.
3. As an Operator, I want the System Status to report "NOMINAL" when the engine is operating correctly at varying throttle levels, so that I do not get fatigued by false alarms.
4. As an Operator, I want the System Status to only report "CRITICAL" when the engine deviates significantly from the *expected physics baseline for that specific throttle*, so that I know when an actual failure is occurring.
5. As a Propulsion Engineer, I want the Twin Comparison widget to display the dynamic expected RPM rather than a hardcoded value, so that I can accurately compare current engine output to its expected output.
6. As a Propulsion Engineer, I want the Twin Comparison widget to display dynamic expected values for Oil Pressure and Oil Temperature, so that I can monitor the lubrication system across different flight phases.
7. As a Propulsion Engineer, I want the Twin Comparison widget to display dynamic expected EGT and CHT values for each individual cylinder, so that I can spot thermal imbalances caused by windmilling or rich/lean conditions.
8. As a System Architect, I want the expected physics calculations to happen purely in the backend simulation, so that the frontend remains lightweight and doesn't duplicate complex domain logic.
9. As a Developer, I want the live MQTT prediction schema to explicitly include `expected_` keys for all relevant parameters, so that parsing on the frontend is straightforward and predictable.

## Implementation Decisions

- **Modules modified:** Backend ML subscriber (`integration/ml_subscriber.py`), frontend telemetry store (`frontend/src/store/useEngineStore.js`), backend test suites.
- **Backend Schema Change:** The MQTT payload published to the predictions topic will be expanded. Alongside the existing `twin_drift_score` and `xgboost_faults`, it will now include `expected_rpm`, `expected_oil_pressure`, `expected_oil_temp`, `expected_cht`, and `expected_egt_1` through `expected_egt_4`.
- **Backend Logic:** The ML subscriber already maintains a localized physics simulation to calculate residuals. It will extract the baseline state directly from this local simulation and bundle it into the prediction payload.
- **Frontend Logic (EHI):** The frontend store will update its telemetry ingestion pipeline to compute `ehi` dynamically. EHI will be calculated as `Math.max(0, Math.round(100 - (data.twin_drift_score * 100)))`, seamlessly mapping a 0 drift to a 100 EHI.
- **Frontend Logic (Expected Values):** The frontend store will stop relying on hardcoded initial fallback values for its twin comparison data structure. It will route the incoming `expected_*` variables from the MQTT prediction payload straight into the global and cylinder-specific deviation logic. 

## Testing Decisions

- **What makes a good test:** External behavior focus. Tests should publish mock telemetry, allow the pipeline to process it, and assert the final shape and content of the JSON payload reaching the boundaries (MQTT topic and WebSocket). Avoid mocking the internal state of the simulation or the store explicitly.
- **Modules to be tested:** The ML subscriber and the WebSocket Gateway test suites.
- **Prior art for the tests:** There are existing tests for the ML subscriber (`tests/test_ml_subscriber.py`) which mock the MQTT broker, publish telemetry, and assert on the prediction output. We will extend these to verify the `expected_*` keys are present and mathematically sensible. The WebSocket gateway test (`tests/test_ws_gateway.py`) currently simulates a payload merge, and this payload will be updated to reflect the new schema.

## Out of Scope

- Introducing new UI widgets or refactoring the React component layouts.
- Modifying the underlying AI model architecture (LSTM, XGBoost, Isolation Forest) or how the `twin_drift_score` is formulated.
- Persisting these dynamic expected values into a database for historical playback (only real-time live view is in scope).

## Further Notes

- By passing the expected baseline from the backend rather than calculating it on the frontend, we prevent duplicate physics logic across the stack. This ensures the Twin Comparison widget directly compares the backend's definitive "healthy baseline" with the "actual telemetry".

## Resolutions & Progress

- **Issue 05 (Dynamic EHI):** COMPLETE. Added `ehi` computation in `_applyTelemetry` in `useEngineStore.js`: `Math.max(0, Math.round(100 - data.twin_drift_score * 100))`. The `EngineHealthWidget` already consumed `ehi` from `missionContext` — no frontend widget changes needed.
- **Issue 06 (Dynamic Physics Baselines):** COMPLETE. Backend `ml_subscriber.py` `_process_tick` now extracts 8 `expected_*` keys from the local simulation's `get_state()` and includes them in the prediction payload. Frontend `_applyTelemetry` routes these into `twinComparisonData.globals.*.expected` and `cylinders[*].egt.expected` / `cylinders[*].cht.expected`, replacing hardcoded baselines. Deviation is now computed against the dynamic physics baseline, eliminating false CRITICAL alarms during healthy throttle changes. Tests in `test_ml_subscriber.py` and `test_ws_gateway.py` updated to assert presence and correctness of `expected_*` keys.
