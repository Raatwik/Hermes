# [wayfinder:task] Datasets: Phase 3 (Cascading Faults & Schema Evolution)

## Problem Statement

The current dataset generation pipeline (`generate_mission.py` and `generate_datasets.py`) relies on a mutually exclusive fault scheduler that can only inject a single fault (or healthy profile) per generated mission. Real-world catastrophic failures, such as the Djibouti MQ-1B accident, often involve a primary fault (like an oil leak) that ultimately causes a secondary catastrophic failure (like a cylinder seizing). Furthermore, the dataset schema needs to be updated to support the new independent cylinder telemetry while ensuring ML training pipelines receive clean data.

## Solution

We will update the `FaultScheduler` to probabilistically support injecting a secondary cascading fault later in the mission timeline. To ensure the ML models can learn from these events, we will add new label columns to the generated dataset. We will also perform a hard wipe of the existing synthetic data to force a clean regeneration with the new schema.

## User Stories

1. As a Data Scientist, I want the automated generator to optionally trigger a secondary cascading fault (e.g., `cylinder_failure` following `lubrication_issues`), so that my ML models can learn to predict catastrophic failure chains.
2. As an ML Engineer, I want the dataset schema to explicitly label `secondary_fault_class` and `secondary_fault_severity` at every timestep, so that I can train models to distinguish between primary and secondary degradations.
3. As an ML Engineer, I want the `generate_datasets.py` bulk orchestrator to delete the old dataset before generation, so that I don't accidentally train on an inconsistent mix of old schema (global EGT only) and new schema (4 cylinders) data.

## Implementation Decisions

- **Fault Scheduler Update:** Modify `FaultScheduler` in `generate_mission.py` to optionally track a second fault. The secondary fault should have its own `injection_time` that is strictly greater than the primary fault's `injection_time`.
- **Schema Addition:** The `record_state` function must be updated to output `secondary_fault_class` (default "none") and `secondary_fault_severity` (default 0.0) for every row.
- **Bulk Orchestrator Clean:** `generate_datasets.py` will use `shutil.rmtree` on the output directory at the very start of the script to guarantee a fresh generation cycle.
- **Backwards Compatibility:** We will not attempt to salvage or migrate the old Parquet files. Generating new data is cheap and fast enough that starting from scratch is the most robust approach.

## Testing Decisions

- **What makes a good test:** Tests should ensure that the generated Parquet files strictly conform to the new schema and properly partition data without throwing schema mismatch errors.
- **Tested Modules:** `datasets.generate_mission`, `datasets.generate_datasets`
- **Test Scenarios:**
  - *Clean Generation:* Run the bulk orchestrator twice in a row. Assert that the output directory only contains the number of missions from the second run (proving the folder wipe works).
  - *Schema Validation:* Load a generated Parquet file using pandas. Assert that `egt_1`, `egt_2`, `egt_3`, `egt_4`, `secondary_fault_class`, and `secondary_fault_severity` columns all exist.
  - *Cascading Logic:* Mock the `FaultScheduler` randomizer to force a secondary fault. Assert that the secondary fault severity is 0.0 before its injection time and grows exponentially afterwards.

## Out of Scope

- Implementing complex, deterministic physical rules for *when* a secondary fault happens based on the primary fault's severity (we will just use probabilistic random timing for now).
