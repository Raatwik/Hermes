# [wayfinder:task] Datasets Phase 2.1: Master Architecture Alignment

## Problem Statement

The current dataset generation pipeline produces realistic exponential degradation and introduces environmental noise, but it lacks specific telemetry fields required by the Digital Twin architecture outlined in the master document (`master.md`). Specifically, the pipeline fails to record the engine's control inputs (throttle) and spatial state (altitude) into the dataset. It also lacks a ground-truth metric for continuous degradation severity, does not simulate engine-to-engine baseline variance (fingerprinting), and lacks contextual flight-phase metadata. Without these elements, downstream ML models cannot accurately learn the expected baseline behaviour for different operating conditions or correctly identify long-term degradation across multiple distinct engines.

## Solution

Update the dataset generation pipeline to fully align with the Master Architecture:
1. Export the control input (`throttle`) and spatial state (`altitude`) explicitly in the dataset.
2. Calculate and export a continuous `fault_severity` (0.0 to 1.0) ground-truth label.
3. Introduce `engine_id` fingerprinting to the `Simulation` class to apply deterministic, engine-specific static offsets to steady-state baselines, and update the bulk orchestrator to assign unique UUIDs to different simulated flights.
4. Update the YAML mission templates to include string names for each phase, and carry this name through to a `flight_phase` column in the final dataset.

## User Stories

1. As an ML Engineer, I want the dataset to include `throttle` and `altitude` for every timestep, so that I can train models that condition expected sensor readings (like EGT and CHT) on the current operating point.
2. As a Data Scientist, I want a `fault_severity` column containing a continuous value from 0.0 to 1.0, so that I can train regression models on the Engine Health Index and continuous degradation rather than just binary fault states or RUL.
3. As a Data Scientist, I want the bulk orchestrator to assign a unique `engine_id` UUID to each generated flight, so that my dataset contains flights from distinctly different engines.
4. As an ML Engineer, I want the `Simulation` class to use the `engine_id` to seed fixed, deterministic offsets to the steady-state baselines, so that I can test my models against engine-to-engine variance and build individual engine fingerprints.
5. As an ML Engineer, I want the `engine_id` to be explicitly recorded in the dataset telemetry, so that I can partition or filter data by individual engine.
6. As a Mission Analyst, I want the dataset to include a `flight_phase` column (e.g., Takeoff, Cruise), so that I can perform phase-wise health reporting and isolate anomalies that only occur during specific mission phases.
7. As a Dataset Engineer, I want the YAML mission configuration to support a `name` key for each phase, so that phase strings are easily configurable and human-readable.

## Implementation Decisions

- **Simulation Interface:** The `Simulation.__init__` method will accept an optional `engine_id` string. If provided, it will seed a random number generator and calculate slight static offsets (e.g., up to +/- 2%) for the base values in `STEADY_STATE_MAP`. These offsets will be applied consistently on every step.
- **Telemetry Exposure:** `Simulation.get_state()` will be updated to include `"throttle"`. `Simulation.get_environment()` will be updated to include `"altitude"`.
- **Fault Severity:** The `record_state` closure in the pipeline orchestrator will fetch the current severity from the `FaultScheduler` and write it to the row as `fault_severity`.
- **Mission Profiles:** The YAML parsing logic will look for a `name` key inside each phase block. This phase name will be attached to the setpoints and interpolated during the simulation loop to populate the `flight_phase` column.
- **Bulk Orchestrator:** The bulk generation script will generate a new `engine_id` UUID for each `MissionTask` and pass it down to the pipeline.

## Testing Decisions

- Tests should primarily target external behavior, not implementation details.
- **Primary Seam (Orchestrator):** The dataset generator orchestrator (`run_pipeline`) will be tested. A test will mock a simple YAML configuration, run the pipeline, and assert that the output Parquet DataFrame contains the columns `throttle`, `altitude`, `fault_severity`, `flight_phase`, and `engine_id`.
- **Secondary Seam (Simulation):** The `Simulation` class will be tested to ensure engine-to-engine variance works. A test will initialize two `Simulation` instances with the same operating parameters but different `engine_id`s, and assert that their sensor outputs (e.g., RPM or CHT) have a slight, persistent difference. A second test will assert that initializing two simulations with the *same* `engine_id` produces identically offset outputs.
- **Prior Art:** Existing tests in `tests/test_pipeline.py` and `tests/unit/test_environment.py` that run the simulation and check Pandas dataframes or sensor states.

## Out of Scope

- Developing the actual Machine Learning models that consume this data (this spec is strictly for generating the data).
- Implementing dynamic degradation based on engine cycles (fingerprint offsets are static for a given `engine_id`).
- Adding entirely new sensors or physical thermodynamics equations to the `STEADY_STATE_MAP`.

## Further Notes

- The addition of `throttle` and `altitude` is absolutely critical for the hybrid physics approach detailed in the master architecture, as the expected engine state is fundamentally dependent on these control/spatial inputs.
