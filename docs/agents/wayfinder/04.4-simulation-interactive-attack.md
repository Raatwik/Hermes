# [wayfinder:task] Simulation: Phase 4 (Interactive Degradation Simulator)

## Problem Statement

The existing "real case simulator" (the Djibouti accident scenario) is hardcoded to a specific 9-hour flight and fault sequence. Users cannot dynamically generate their own scenarios. We need a flexible, interactive replacement focused on **prediction (prognostics/Remaining Useful Life)**. It should allow the user to choose the types of engine faults (attacks) to inject and simulate them in a progressive **degradation manner** (gradually worsening over time). This flexibility is necessary to rapidly generate varied failure datasets for testing predictive models and evaluating our multi-output classification and prognostic capabilities.

## Solution

Replace the static accident scenario with a new interactive attack scenario module. This module will present a command-line menu to the user, allowing them to selectively configure one or more faults, define a progressive degradation timing strategy, and execute a standard baseline mission profile. Telemetry will be exported for downstream machine learning evaluation.

## User Stories

1. As a tester, I want to be presented with an interactive command-line menu upon launching the simulator, so that I can configure the simulation without modifying source code.
2. As a tester, I want to see a comprehensive list of all supported engine faults (e.g., misfire, sensor drift, cylinder failure), so that I can choose which specific anomaly to inject.
3. As a data scientist, I want to be able to select multiple faults in a single simulation run, so that I can test compound failure conditions and multi-output ML model accuracy.
4. As a tester, I want the simulator to loop the fault selection menu until I explicitly indicate I am done, so that I can add as many overlapping faults as needed.
5. As an ML engineer, I want the injected faults to exhibit progressive degradation (exponentially worsening over time), so that the simulation accurately represents gradual mechanical wear rather than instantaneous failure.
6. As a tester, I want to be prompted to enter a "Target Time to Failure" duration, so that I can control the rate at which the exponential degradation reaches critical severity.
7. As an ML engineer, I want the simulator to automatically run a standardized 1-hour flight profile (Takeoff, Climb, Cruise, Loiter, Return, Land), so that my models are tested against a consistent operational baseline.
8. As a data scientist, I want the simulation to export raw telemetry to a CSV format matching the schema of our ML pipeline, so that I can seamlessly pass the data to prediction algorithms.
9. As a data scientist, I want the simulator to intentionally omit post-calculated metrics like Remaining Useful Life (RUL) from the CSV, so that the standard downstream labeling pipeline remains the single source of truth for RUL calculation.
10. As a tester, I want the simulation to continuously monitor the engine state against physical failure thresholds, so that the simulation stops accurately when the engine seizes.
11. As an ML engineer, I want the simulator to catch engine failure exceptions and terminate cleanly while saving the final telemetry, so that the exact moment of catastrophic failure is recorded as the zero-anchor for prognostic models.

## Implementation Decisions

- **Architecture:** We will replace the existing static accident scenario script with a new interactive CLI module.
- **Progressive Degradation Mechanics:** We will utilize the existing exponential degradation logic (from the existing fault scheduler component) to smoothly ramp the severity of any selected fault from 0.0 up to 1.0.
- **Target Time to Failure Input:** The module will interactively request a user-defined "Target Time to Failure" duration, which will calculate the curve parameters (alpha) required to scale the degradation curve to hit 100% severity at that exact duration after injection.
- **Compound Fault State:** The module will iteratively collect fault selections and apply them to the centralized fault manager. The fault manager natively supports concurrent anomalies, and no structural changes are needed to support simultaneous degradation.
- **Flight Profile Execution:** The simulator will initialize a 1-hour baseline profile with diverse throttle and altitude setpoints mapped to standardized phases (Takeoff through Landing).
- **Telemetry Contract:** A standard CSV writer will serialize the engine's raw state telemetry output row-by-row. We explicitly will not calculate or append RUL features within this module; raw data only.

## Testing Decisions

- **What makes a good test:** Tests should verify external simulation behavior—specifically, that compound telemetry patterns emerge in the output and that the simulation respects physical boundaries without exposing internal component logic.
- **Modules to be tested:** The interactive scenario module and its integration with the core simulation engine.
- **Testing Scenarios:**
  - *Compound Degradation Test:* Run the module, select at least two distinct faults, provide a moderate Target Time to Failure, and verify the resulting CSV file contains gradually appearing signatures for both faults.
  - *Catastrophic Termination Boundary:* Run the module with an aggressive Target Time to Failure and verify that it terminates execution precisely when physical parameters cross critical thresholds, rather than continuing the simulation indefinitely.

## Out of Scope

- Implementing entirely new attack vectors (e.g., cyber-attacks, GPS spoofing) not currently supported by the underlying physical fault manager.
- Modifying the core simulation engine's thermodynamic equations.
- Performing live RUL prediction visualization during the simulation itself.

## Further Notes

- The downstream labeling pipeline must be made aware of this new telemetry source so it can properly apply Remaining Useful Life (RUL) annotations based on the exact simulation termination timestamp.
