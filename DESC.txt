• ﻿Project Hermes   Proposed Solution (SIH National Level).
• The Central Question Hermes Answers:.
• Not just "Is the engine abnormal right now?" but:.
• What is its current degradation state, what will happen during the planned mission, why is that outcome predicted, and which feasible operating alternative reduces that risk?.
• BLOCK 1   Why Static Monitoring Fails (The Problem Frame).
• Context-Blind Threshold Monitoring is Operationally Dangerous.
• Legacy aero-engine monitoring uses fixed alarm thresholds.
• The same EGT value at takeoff (high load, sea level) and at 6,000m cruise means entirely different things.
• Hermes evaluates every engine reading against condition-aware expected behaviour generated by a physics model   not a fixed number.
• Fixed thresholds that ignore altitude, load, RPM and mission phase will always produce false alarms or missed faults.
• Hermes does not.
• BLOCK 2   The Technical Core: Physics + State Estimation Pipeline.
• 1 PINN + ODE Physics Model.
• - A Reduced-Order Mean Value Engine Model (MVEM) encodes thermodynamic relationships: combustion efficiency, volumetric efficiency, thermal transfer, lubrication state.
• - At every timestep, the model outputs expected engine behaviour given current operating conditions (altitude, throttle, RPM, ambient temp).
• - The physics model is the ground-truth reference the AI continuously checks reality against.
• - Key claim: Every AI prediction in Hermes is anchored to thermodynamic relationships.
• The system cannot recommend an action that violates physics.
• 2 UKF (Unscented Kalman Filter)   State Estimator.
• - Engine dynamics are nonlinear.
• UKF handles nonlinearity without full model linearization (unlike EKF).
• - Purpose: Fuse noisy, incomplete sensor telemetry with PINN/ODE predictions to produce smoothed, continuously updated internal engine state estimates.
• - Estimates latent health variables that cannot be directly measured: combustion efficiency, injector condition, lubrication state, mechanical friction.
• - Role in pipeline: PINN/ODE → UKF State Estimation → Fault Detection → RUL Prediction.
• - Why it matters: Downstream ML models receive clean, physically-grounded inputs rather than raw noisy sensor readings.
• Garbage in, garbage out   UKF prevents garbage in.
• 3 Physics-Based Residual Analysis.
• - Core diagnostic signal: Residual = Actual Sensor Reading − Physics-Expected Reading.
• - A healthy engine produces near-zero residuals across all sensors.
• - Persistent, multi-sensor divergence triggers the diagnostic chain   not a single spike, which could be noise.
• 4 Individual Engine Fingerprinting.
• - A generic fleet-average baseline is insufficient.
• Manufacturing tolerances mean Engine A normal vibration is 1.
• 5g; Engine B is 1.
• - Hermes builds a per-engine behavioural baseline using one-class modelling on historical sortie data.
• - Anomaly detection fires when an engine deviates from its own norm, not a population average.
• - Outcome: Fewer false alarms, earlier detection of subtle progressive degradation, better RUL accuracy.
• BLOCK 3   Fault Intelligence: Detection, Diagnosis, Isolation.
• 1 Three-Way Fault Triage.
• Residual divergence does not automatically mean engine failure.
• Hermes classifies into three cases:.
• Category   Signature Pattern   Response.
• Sensor Fault / Drift   Single sensor residual spikes; all others nominal   Sensor isolation → Flag as instrumentation fault, not engine fault.
• Twin Model Mismatch   Broad residual increase after operating regime shift   Model recalibration trigger   "The twin, not the engine, is wrong".
• A false alarm grounding a UAV mid-surveillance mission has operational cost equivalent to a real fault.
• Sensor-engine fault separation is not optional.
• 2 Zero-Day / Open-Set Fault Detection.
• - Supervised XGBoost classifies known fault types (injector degradation, oil starvation, overheating, misfire).
• - Isolation Forest runs in parallel as the open-set anomaly detector.
• - If telemetry does not match any known fault signature: output is "NOVEL ANOMALY   outside training distribution", not a forced misclassification.
• - In a safety-critical system, confidently reporting an unknown unknown is more operationally valuable than incorrectly labelling it as a known fault.
• 3 Multimodal Acoustic + Vibration Fusion (Digital Stethoscope).
• - Piezoelectric accelerometers and onboard microphones stream vibration and acoustic data alongside standard telemetry.
• - Audio Spectrogram model detects: bearing wear, valve timing drift, combustion knock, mechanical imbalance.
• - These signatures appear hours before they cause measurable changes in EGT, CHT or oil pressure.
• - The USP: Sub-component fault detection before thermodynamic degradation begins.
• Hermes does not just read the engine vitals   it listens to its heartbeat.
• BLOCK 4   Health Output.
• 1 Engine Health Index (EHI).
• - A single composite scalar: 100 (pristine) → 0 (imminent failure).
• - Inputs: UKF-cleaned sensor states, residual magnitudes, degradation trajectory, RUL estimate.
• - An operator cannot act on 14 sensor graphs during a high-stress sortie.
• One number they can act on immediately.
• This is what makes Hermes a health monitoring system, not just a data dashboard.
• 2 Uncertainty-Aware RUL via Monte Carlo Dropout LSTM.
• - Standard LSTM outputs a single RUL point estimate.
• That is not actionable for a safety-critical Return-To-Base decision.
• - Hermes uses MC Dropout LSTM (Gal & Ghahramani, ICML 2016): Dropout is kept active at inference.
• N=50 stochastic forward passes generate a full predictive distribution.
• - Captures both aleatoric uncertainty (model own sigma via NLL training) and epistemic uncertainty (variance across MC passes).
• - A pilot can make a life-or-death RTB decision on a confidence interval.
• They cannot on a black-box point estimate.
• BLOCK 5   Mission Intelligence (The Core Differentiator).
• The problem statement title includes "Mission Reliability Enhancement.
• " Most teams ignore this entirely.
• Hermes makes it the centrepiece.
• 1 Future Mission Simulation.
• - Given: current EHI + planned mission profile (altitude curve, throttle, duration, ambient conditions).
• - Hermes simulates the engine degradation trajectory across the entire upcoming mission.
• - Output: predicted end-of-mission engine health, RUL margin at completion, Mission Completion Risk Score (0 100%).
• - "Before the UAV takes off, Hermes already knows if it can land safely.
• 2 Counterfactual "What-If" Prescriptive Engine.
• - Does not just report risk.
• Asks: what operating changes would reduce it?.
• - Simulates alternative mission profiles (varied altitude, throttle, duration) and computes risk delta for each.
• - Prescriptive, not just predictive.
• Decision support, not autonomous control   operator accepts or rejects.
• 3 Constraint-Aware Mission Optimization.
• - Lowest engine-risk scenario does not equal the correct operational choice.
• - System filters counterfactual alternatives against hard mission constraints: minimum surveillance duration, required altitude corridor, fuel endurance, operating region.
• - Output: Safest feasible option, not just safest option.
• BLOCK 6   Defense-Specific Layer.
• 1 Adversarial Sensor Spoofing Detection.
• - In contested environments (EW, jamming), sensor signals can be corrupted or spoofed.
• - Because Hermes maintains a continuously updated physics-based expected state, readings that are thermodynamically impossible trigger a dedicated flag: "Spoofed / corrupted sensor   physical impossibility detected" rather than generating a false fault diagnosis.
• - Example: Oil pressure dropping 40 PSI in 0.
• 3 seconds violates the thermodynamic model.
• Hermes flags it as a sensor integrity issue, not an oil pump failure.
• - This requires a physics model to have a reference for "physically impossible.
• " Purely data-driven systems cannot detect this.
• No other team will have thought of it.
• BLOCK 7   Supporting Architecture.

• - Hermes generates synthetic fault data by injecting faults at the physical parameter level (injector flow coefficient, thermal transfer rate, friction coefficient).
• - Faulty sensor signatures emerge from the physics   they are not artificially added noise.
• - Outcome: Labeled training data reflecting real causal fault physics, covering fault types that may never have occurred in real fleet history.

• Hermes: MALE-UAV Aero-Piston Engine AI Digital Twin.
• Hermes is an AI-enabled, mission-aware Digital Twin designed for aero-piston engines (specifically modeling a naturally aspirated Rotax 914) used in Medium Altitude Long Endurance (MALE) UAVs.

• [wayfinder:task] Simulation: Engine Physics & Twin Core.
• Problem Statement.
• The user needs a physically plausible simulation of a Rotax 914 engine to generate baseline telemetry and synthetic fault data.
• This data is critical for training and evaluating predictive analytics models (such as diagnostics and Remaining Useful Life (RUL)) for a MALE-UAV Digital Twin, as relying solely on real-world anomalous flight data is impractical, scarce, and dangerous to acquire.
• A Python-based simulation engine using a Mean-Value Engine Model (MVEM) approach.
• It will use empirical lookup tables combined with first-order lag filters to model steady-state and transient behaviors without the computational overhead of solving complex ODEs.
• The simulation will provide a Python API to explicitly step through time, driven by scriptable mission profiles.
• A centralized FaultManager will allow users to dynamically inject faults at runtime, predictably altering the telemetry to reflect conditions like misfires, sensor drift, and cooling degradation.
• User Stories.
• As an ML Engineer, I want the simulation to output baseline telemetry (RPM, CHT, EGT, Oil Press/Temp, Fuel Flow, Vibration, Battery, Injection), so that I can train models on normal operating conditions.
• As a Data Scientist, I want to load scriptable mission profiles (throttle, altitude, ambient temp), so that I can generate reproducible operational scenarios.
• As an ML Engineer, I want to explicitly step the simulation time forward via a step(dt) API, so that I can generate training datasets significantly faster than real-time.
• As an ML Engineer, I want to query the current telemetry state via a get_state() API, so that I can capture the output at any point in the time series.
• As an Operator, I want the simulation to realistically model transient responses using first-order lag filters, so that the engine doesn't instantly snap to new states when throttle changes.
• As a Tester, I want to dynamically inject a "sensor drift" fault via the API, so that I can evaluate if the predictive model catches gradual sensor degradation over time.
• As a Tester, I want to dynamically inject a "cooling degradation" fault, so that I can simulate a blocked radiator and see CHT and Oil Temp rise.
• As a Tester, I want to dynamically inject a "misfire" fault, so that I can observe the effect on RPM stability, EGT, and vibration.
• As a Tester, I want to inject "injector abnormalities", so that I can see corresponding changes in fuel flow and EGT.
• As a Tester, I want to simulate "lubrication issues", so that I can observe drops in oil pressure and spikes in oil temperature.
• As an ML Engineer, I want vibration to be modeled as an abstract 0.
• 0 severity index, so that I have a lightweight representation of mechanical health without the overhead of processing high-frequency audio/accelerometer data.
• Implementation Decisions.
• - A main Simulation class will serve as the primary API boundary, exposing loadprofile(profiledata), step(dt), getstate(), and injectfault(fault_type, kwargs) methods.
• - The core physics will rely on empirical maps (e.
• , dictionaries or data structures mapping throttle and altitude to steady-state target values for temperatures and pressures).
• - Transient states (like temperatures taking time to heat up/cool down) will be managed by a LagFilter utility class that implements an exponential moving average based on the time step dt and a physical time constant.
• - A centralized FaultManager will intercept calculations.
• When step(dt) is called, the Simulation will ask the FaultManager for active fault modifiers and apply them to the current state (e.
• , adding an offset to the final sensor output, or changing the time constant of a lag filter).
• - Mission profiles will be defined as structured objects (e.
• , parsed from JSON or YAML) containing arrays of timestamped setpoints.
• The simulation will linearly interpolate between these setpoints during step(dt).
• - Vibration will not use FFTs or time-domain waveforms; it will simply be a derived value based on engine speed and active mechanical faults.
• Testing Decisions.
• - What makes a good test: Tests will solely assert against the external behavior (the telemetry dictionary output from getstate()) in response to public API inputs (step, injectfault, load_profile).
• We will avoid testing the internal state of the FaultManager, the precise values inside the empirical maps, or the internal state variables of the filters.
• - Tested Modules: The public interface of the Simulation engine package.
• - Prior Art: (None yet; this is the foundational simulation component).
• - Test Scenarios:.
• - Baseline Test: Initialize simulation, step for 100 seconds at a constant 50% throttle, assert CHT and EGT stabilize within plausible bounds and do not oscillate.
• - Transient Test: Step at 50% throttle until stable, instantly change throttle to 80%, step for 5 seconds, assert CHT is rising but has not instantly snapped to the new maximum (verifying lag filters).
• - Fault Test: Step to steady state, invoke sim.
• injectfault('coolingdegradation'), step for another 50 seconds, assert CHT and Oil Temp are strictly greater than the baseline steady state.
• Out of Scope.
• - Real-time message brokering (MQTT/ZeroMQ).
• The simulation only provides a synchronous Python API.
• A separate integration script/module will be responsible for calling step() and publishing the outputs to a broker.
• - Full 3D kinematic modeling of the drone airframe (we are exclusively modeling the engine).
• - High-frequency time-domain vibration audio/accelerometer data.
• - Solving complex differential equations for physical thermodynamics (we are substituting this with maps and filters).

• 3 Simulation Remediation - Engine Failure Thresholds.
• Context / Problem Statement.
• Currently, the engine simulation runs for a fixed duration regardless of the severity of the faults injected.
• When a catastrophic physical fault is injected (e.
• , severe cooling degradation leading to extreme CHT, or massive misfire causing RPM drop), the simulation continues logging data until the predetermined maxtime.
• As a result, the downstream ML pipeline calculates the Remaining Useful Life (RUL) as a simple countdown timer (maxtime - current_time), training the LSTM model to falsely believe that catastrophically damaged engines survive just as long as perfectly healthy ones.
• The simulation engine must be updated to inherently recognize catastrophic failure states.
• When critical telemetry thresholds are breached (e.
• , RPM drops below idle, or temperatures exceed structural limits), the simulation should terminate early.
• This physical termination naturally shortens the generated data file.
• Consequently, the existing RUL calculation in the ML pipeline will automatically assign correct, responsive labels (reaching 0 at the moment of catastrophic failure).
• As a Simulation Engineer, I want the engine simulation to halt execution immediately when RPM drops below 1000, so that engine stall conditions are realistically modeled.
• As a Simulation Engineer, I want the engine simulation to halt execution immediately when Cylinder Head Temperature (CHT) exceeds 250°C, so that catastrophic thermal failure is modeled.
• As a Simulation Engineer, I want the engine simulation to halt execution immediately when Oil Pressure drops below 20 psi, so that fatal lubrication failure is modeled.
• As a Simulation Engineer, I want the engine simulation to halt execution immediately when Exhaust Gas Temperature (EGT) exceeds 900°C, so that critical exhaust valve/turbine failure is modeled.

• [wayfinder:task] Simulation: Phase 4 (Interactive Degradation Simulator).
• The existing "real case simulator" (the Djibouti accident scenario) is hardcoded to a specific 9-hour flight and fault sequence.
• Users cannot dynamically generate their own scenarios.
• We need a flexible, interactive replacement focused on prediction (prognostics/Remaining Useful Life).
• It should allow the user to choose the types of engine faults (attacks) to inject and simulate them in a progressive degradation manner (gradually worsening over time).
• This flexibility is necessary to rapidly generate varied failure datasets for testing predictive models and evaluating our multi-output classification and prognostic capabilities.
• Additionally, the simulator currently does not output any Remaining Useful Life (RUL) metrics, relying on downstream ML components (like an LSTM model).
• This is problematic when users want to treat the simulator output as ground truth or visualize RUL directly without running the complex ML pipeline, which can lead to unpredictable or delayed evaluations of the RUL.
• Replace the static accident scenario with a new interactive attack scenario module.
• This module will present a command-line menu to the user, allowing them to selectively configure one or more faults, define a progressive degradation timing strategy, and execute a standard baseline mission profile.
• Telemetry will be exported for downstream machine learning evaluation.
• To resolve the RUL dependency, the script will directly compute and export a hardcoded RUL column in its CSV output based on the injected attack type.
• To prevent erratic frontend updates, this RUL metric will decrement in 10-second discrete steps rather than updating every second.
